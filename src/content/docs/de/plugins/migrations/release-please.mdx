Diese Anleitung unterstützt Teams beim Umstieg von release-please auf semrel, ohne Release-Governance zu verlieren.

## Mapping auf einen Blick

| release-please Verhalten | semrel Entsprechung |
| --- | --- |
| Release-PR mit Versions-/Changelog-Änderungen | semrel Analyzer + Generator-Ausgaben in CI |
| Tag und Release nach Merge | semrel Provider + Publish-Stufen |
| PR-Transparenz und Review-Gate | Branch-Protection beibehalten, semrel nach Merge ausführen |

## Empfohlenes Rollout

<Steps>

1. release-please PR-Flow vorübergehend für Audit-Transparenz beibehalten.
2. semrel Dry-Run auf gemergten PRs ausführen und Version/Changelog vergleichen.
3. Version/Changelog-Ownership auf semrel-Plugins umstellen.
4. Publishing und Tag-Ownership auf semrel verlagern.
5. release-please Release-Erstellung deaktivieren, um doppelte Tags/Releases zu verhindern.

</Steps>

## Beispiel-Plugin-Basis

```yaml
plugins:
  - uses: @semrel/github

  - uses: @semrel/conventional

  - uses: @semrel/release-notes

  - uses: @semrel/changelog-md
    args:
      file: CHANGELOG.md
```

<Aside type="note">
  Wenn euer Prozess explizite Release-Reviews verlangt, behaltet ein PR-Gate im Workflow bei, stellt aber sicher, dass genau ein System Release-Tags erstellt.
</Aside>

## Risiken und Checks

- release-please und semrel dürfen nie gleichzeitig Tags erzeugen.
- Monorepo-Paketversionsverhalten vor dem Cutover prüfen.
- Rollback testen, indem der bisherige Workflow für einen Zyklus verfügbar bleibt.
