Diese Anleitung richtet sich an Teams, die von semantic-release auf semrel migrieren.

## Mapping auf einen Blick

| semantic-release Bereich | semrel Entsprechung |
| --- | --- |
| Commit-Analyzer-Plugins | Analyzer-Plugin (`analyzer-default` / `analyzer-conventional`) |
| Release-Notes-/Changelog-Plugins | Generator-Plugins (`generator-release-notes`, `generator-changelog-*`) |
| npm/github/docker Publish-Plugins | Publisher-Plugins (`publisher-oci`, `publisher-generic-http`) + CI-Publish-Jobs |

## Empfohlenes Rollout

<Steps>

1. Branch- und Trigger-Policy zunächst unverändert lassen.
2. semrel im Dry-Run ergänzen und Version + Notes mit semantic-release vergleichen.
3. Changelog/Release Notes auf semrel-Generatoren umstellen.
4. Publishing von semantic-release auf semrel-Publisher migrieren.
5. semantic-release Tagging/Publishing nach einem stabilen Zyklus deaktivieren.

</Steps>

## Typische semrel-Basis

```yaml
plugins:
  - uses: @semrel/provider-github

  - uses: @semrel/analyzer-conventional

  - uses: @semrel/generator-release-notes

  - uses: @semrel/generator-changelog-md
    args:
      file: CHANGELOG.md
```

## Beispiele für Publishing-Ersatz

- npm-Paketfluss: `npm publish` im CI beibehalten, nachdem semrel Version und Changelog bestimmt hat.
- GitHub-Release-Assets: Upload über CI-Schritt oder plugin-basiertes Publishing.
- OCI-/generische Artefakte: `@semrel/publisher-oci` oder `@semrel/publisher-generic-http` verwenden.

<Aside type="tip">
  Wenn du semantic-release Channels wie `next` oder `beta` nutzt, bilde sie über branch-spezifische semrel-Konfigurationen ab und vermeide geteilte Tag-Ownership zwischen Branches.
</Aside>

## Risiken und Checks

- Sicherstellen, dass nur ein System Tags erstellt.
- Mindestens 10 aktuelle Commits im Dry-Run vergleichen, um Versions-Parität zu prüfen.
- Credentials in `SEMREL_PLUGIN_*` Umgebungsvariablen verschieben.
