## Warum semrel?

<CardGrid stagger>
  <Card title="Keine manuelle Versionierung" icon="approve-check">
    semrel analysiert eure [Conventional Commits](https://www.conventionalcommits.org/) und entscheidet automatisch, ob `major`, `minor` oder `patch` erhöht wird — ohne manuelles Eingreifen.
  </Card>
  <Card title="Vollständig plugin-basiert" icon="puzzle">
    Jeder Schritt der Pipeline ist ein austauschbares Subprocess-Plugin. GitHub-Provider durch GitLab ersetzen, den Changelog-Generator tauschen oder Slack-Benachrichtigungen hinzufügen — alles ohne Änderungen am Core.
  </Card>
  <Card title="Monorepo-ready" icon="seti:folder">
    Mehrere unabhängige Module in einem Repository versionieren, jedes mit eigenem Tag-Series und Konfigurationsdatei.
  </Card>
  <Card title="Supply-Chain-Security" icon="shield">
    Signierte Releases mit Sigstore Cosign, CycloneDX/SPDX SBOM, SLSA Level 1 Provenance. DCO Sign-off und REUSE/SPDX-Compliance bei jedem PR.
  </Card>
  <Card title="Sprachunabhängige Plugins" icon="translate">
    Plugins sind einfache Subprocess-Binaries — sie können in Go, Python, Rust, Node.js oder jeder anderen Sprache geschrieben werden.
  </Card>
  <Card title="Dry-run-Modus" icon="information">
    Vorher genau sehen, was semrel tun würde. `semrel release --dry-run` validiert die Konfiguration sicher, ohne etwas zu verändern.
  </Card>
  <Card title="Open Source" icon="open-book">
    Apache 2.0 lizenziert. Offen entwickelt auf [SemRels/semrel](https://github.com/SemRels/semrel).
  </Card>
</CardGrid>
