## semrel vs semantic-release

**semantic-release** ist ein commit-getriebenes Release-Tool mit einem erweiterbaren JavaScript-Plugin-Ökosystem. semrel bietet einen ähnlichen commit-getriebenen Workflow als Go-Binärdatei; Konfiguration und Plugin-APIs unterscheiden sich jedoch.

### Node.js-Runtime und Abhängigkeiten

Die Integration von semantic-release in eine Go-, Rust- oder C++-Pipeline erfordert:

```bash
# Eine unterstützte Node.js-Runtime und semantic-release
# samt den benötigten Plugins installieren.
actions/setup-node@v4
npm install --save-dev semantic-release
```

Das ergänzt einen Job, der sonst vielleicht nur ein Go-Executable benötigt, um eine Node.js-Runtime und npm-Pakete. Setup-Zeit und Abhängigkeitsanzahl hängen von Runner, Lockfile und konfigurierten Plugins ab.

semrel ersetzt den gesamten Block durch:

```bash
curl -L https://github.com/SemRels/semrel/releases/latest/download/semrel_linux_amd64.tar.gz | tar -xz
./semrel release
```

### Performance

Wir haben denselben lokalen Dry-Run für Versionsberechnung und Release Notes in einem isolierten Checkout auf Basis von Flutter stable 3.44.8 ausgeführt. Der Checkout enthält 2.807.240 getrackte Zeilen in Source- und Konfigurationsdateien sowie 15.665 getrackte Dateien; die vollständige lokale History umfasst 89.116 Commits und 1.102 Tags. Am HEAD des Checkouts wurde ein v3.44.8-Benchmark-Baseline-Tag erstellt, gefolgt von 201 Test-Commits. Alle drei Tools ermittelten v3.44.9.

| Tool | Median | p90 |
|---|---:|---:|
| semrel v0.28.3 | 1,85 s | 2,13 s |
| semantic-release v26.0.1 | 1,19 s | 1,27 s |
| release-it v21.1.2 | 3,83 s | 4,31 s |

Methode: ein Warm-up, danach 10 gemessene Dry-Runs pro Tool, abwechselnd im selben lokalen Checkout und mit lokalem Git-Remote. Der gemessene Zeitraum umfasste den synthetischen v3.44.8-Baseline-Tag, einen Setup-Commit und 200 synthetische Conventional Commits; Flutter-Quelldateien blieben unverändert. Publishing und Paketinstallation waren ausgeschlossen. Der Runner war WSL2/Linux x86_64 auf einem Intel Core Ultra 7 265H mit 10 logischen CPUs; für die JavaScript-Tools lief Node.js v26.13.0. Diese Tools lesen die Git-History, nicht alle Source-Zeilen; Commit-Zeitraum und Plugins bestimmen die Last stärker als die LOC-Zahl allein. GoReleaser verwendet einen vorhandenen Tag, release-please arbeitet mit GitHub-PR/API und Changesets mit manuell angelegten Change-Dateien. Diese Tools erledigen nicht dieselbe lokale Commit-zu-Version-Aufgabe und sind deshalb nicht in der Laufzeittabelle enthalten.

### Supply-Chain-Angriffsfläche

semantic-release und die konfigurierten Plugins verwenden das Node.js-/npm-Ökosystem. Der genaue Abhängigkeitsbaum hängt von Version und Projekt-Lockfile ab.

Der semrel-Kern wird als Go-Executable verteilt; optionale Plugins sind separate Artefakte, die in `.semrel.lock` per Prüfsumme gepinnt werden. In beiden Fällen müssen Abhängigkeiten, Provenienz, Zugangsdaten und CI-Berechtigungen geprüft werden.

### Scope-basierte Release-Regeln

Sowohl semrel als auch semantic-release unterstützen die Zuweisung von Commits zu Bump-Leveln anhand des Scopes. Das Feld `scope` in semrel ist optional — und unterstützt auch `scope: false`, um nur Commits _ohne_ Scope zu matchen:

```yaml
# semrel (.semrel.yaml)
rules:
  - type: deps
    scope: major
    bump: major
  - type: deps
    scope: minor
    bump: minor
  - type: deps
    scope: patch
    bump: patch
  - type: feat
    bump: minor
```

```json
// semantic-release (package.json)
{
  "releaseRules": [
    { "type": "deps", "scope": "major", "release": "major" },
    { "type": "deps", "scope": "minor", "release": "minor" }
  ]
}
```

3. `semrel release --dry-run` ausführen und das Ergebnis mit dem bisherigen Workflow vergleichen

</Card>

## semrel vs goreleaser

goreleaser und semrel lösen **unterschiedliche Probleme** und werden häufig zusammen eingesetzt.

| Frage | semrel | goreleaser |
|---|---|---|
| **Welche Version soll released werden?** | ✅ Berechnet aus Commits | ❌ Du gibst den Tag vor |
| **Cross-Kompilierung (linux/arm64, darwin/amd64 …)** | ❌ Nicht zuständig | ✅ Kernfunktion |
| **GitHub/GitLab-Release mit Artefakten** | ✅ Via Provider-Plugins | ✅ Kernfunktion |
| **Changelog generieren** | ✅ Via Generator-Plugins | Teilweise (via Templates) |
| **Docker, Homebrew, npm, PyPI veröffentlichen** | ✅ Via Updater + Packager + Publisher Plugins | ✅ Docker/Homebrew und Paket-Publishing; einige Ziele sind Pro |
| **Monorepo-Versionierung** | ✅ Native Workspaces | ✅ GoReleaser Pro |

**Empfohlener kombinierter Workflow:**

```yaml
# GitHub Actions
- name: Nächste Version berechnen
  run: semrel release --dry-run --output json > semrel-output.json

- name: Artefakte bauen & verteilen
  uses: goreleaser/goreleaser-action@v6
  with:
    args: release
  env:
    GORELEASER_CURRENT_TAG: ${{ fromJson(steps.prev.outputs.json).nextVersion }}
```

<Aside type="note">
  Wenn du nur automatische Versionierung und ein Standard-Forge-Release benötigst — aber keine Multi-Plattform-Kompilierung — kann semrel ausreichen. GoReleaser ist für den Build und die Verteilung von Release-Artefakten ausgelegt. GoReleaser Pro ergänzt kommerzielle Funktionen; aktuelle Pläne und Preise findest du in der [offiziellen Dokumentation](https://goreleaser.com/pro/).
</Aside>

Die ausführliche Schritt-für-Schritt-Migrationsanleitung findest du unter [Von goreleaser zu semrel](/de/plugins/migrations/goreleaser/).

## semrel vs release-please

**release-please** (von Google) verwendet im Standard-Workflow ein **Pull-Request-First-Modell**. Statt bei jedem Push zu releasen:

1. Sammelt es Commits in einem „Release-PR"
2. Ein Mensch merged den PR, um das Release auszulösen

| Frage | semrel | release-please |
|---|---|---|
| **Vollautomatisch (kein PR-Gate)** | ✅ | ❌ PR erforderlich |
| **Conventional Commits** | ✅ | ✅ |
| **Forge-Integration** | ✅ GitHub, GitLab, Gitea/Forgejo, Bitbucket und plain Git | Auf GitHub ausgerichteter Workflow |
| **Erweiterungsmodell** | ✅ Externe ausführbare Plugins | Eingebaute Release-Strategien und Component-Manifeste |
| **Node.js-Abhängigkeit** | ❌ Keine | ✅ Erforderlich |

Wähle release-please, wenn dein Team eine menschliche Freigabe vor jedem Release benötigt. Wähle semrel für vollständig automatisierte CI-Releases oder Nicht-GitHub-Forges.

Die ausführliche Schritt-für-Schritt-Migrationsanleitung findest du unter [Von release-please zu semrel](/de/plugins/migrations/release-please/).

## semrel vs release-it

**release-it** ist ein JavaScript-Release-Tool mit interaktivem CLI-Modus. Die aktuelle v21-Linie unterstützt GitHub- und GitLab-Integrationen; Conventional-Commit-basierte Versionsvorschläge gibt es über das conventional-changelog-Plugin.

| Frage | semrel | release-it |
|---|---|---|
| **Runtime** | Keine | Node.js + npm |
| **Conventional-Commit-Auto-Bump** | ✅ | ✅ über conventional-changelog-Plugin |
| **Scope-basierte Bump-Regeln** | ✅ | Abhängig von Plugin/Konfiguration |
| **Interaktiver Release-Wizard** | ❌ | ✅ |
| **Offline-Nutzung** | Plugin-Wiederherstellung kann aus dem Lockfile vorbereitet werden; Remote-Publishing benötigt Netzwerk | Lokale Git-Schritte sind offline möglich; Remote-Publishing benötigt Netzwerk |
| **Abhängigkeitsmodell** | Eigenständiger Kern; separate Plugins | Node.js-Paket und Plugins |
| **Forge-Integrationen** | ✅ GitHub, GitLab, Gitea/Forgejo, Bitbucket und plain Git | GitHub- und GitLab-Integrationen |
| **Plugin-Sprache** | **Beliebige Binärdatei** | Nur JS |

release-it eignet sich gut für JavaScript/TypeScript-Projekte, die Node.js bereits in CI nutzen und eine interaktive Erfahrung wünschen. semrel ist eine Alternative, wenn eine Go-Binärdatei und externe ausführbare Plugins besser zum Stack passen.

## semrel vs changesets

**Changesets** (v3) ist auf JavaScript/TypeScript ausgerichtet und bittet Beitragende, Changeset-Dateien für Paketänderungen anzulegen. Der Release-Plan leitet Bump-Level nicht automatisch aus Conventional-Commit-Nachrichten ab.

| Frage | semrel | changesets |
|---|---|---|
| **Versionsquelle** | Conventional Commits und konfigurierte Regeln | Explizite Changeset-Dateien, meist in einem PR angelegt |
| **Bump aus Conventional Commits** | ✅ | ❌ |
| **Multi-Package-Workflow** | Native Workspace-Unterstützung | Kernanwendungsfall |
| **Nicht-JS-Projekte** | ✅ | ❌ Für JS/TS konzipiert |
| **Runtime** | Keine | Node.js + npm |

Wähle semrel, wenn Versionssprünge aus Commit-Nachrichten und Regeln abgeleitet werden sollen. Changesets eignet sich für JS-Monorepos, in denen Beitragende die gewünschte Versionsänderung für jedes Paket explizit festhalten.

## Entscheidungshilfe

```
Brauchst du kein Node.js in deiner Pipeline?
  → Ja   → semrel ✅
  → Nein → jedes Tool geeignet

Brauchst du Versions-/Build-Schritte offline auszuführen?
  → Ja   → semrel, GoReleaser, release-it oder Changesets können lokale Schritte offline ausführen, sobald Abhängigkeiten verfügbar sind
  → Nein → jedes Tool geeignet

Brauchst du automatische Versionierung aus Commit-Nachrichten?
  → Ja   → semrel, semantic-release oder release-it
  → Nein → goreleaser (tag-basiert)

Brauchst du Scope-basierte Bump-Regeln (z. B. deps(major))?
  → Ja   → semrel oder semantic-release ✅
  → Nein → jedes Tool geeignet

Brauchst du Cross-Plattform Go-Binärkompilierung?
  → Ja   → goreleaser (kann mit semrel kombiniert werden)
  → Nein → semrel reicht

Möchtest du PR-Genehmigung vor dem Release?
  → Ja   → release-please
  → Nein → semrel ✅

Ist dein Projekt ausschließlich JavaScript/TypeScript?
  → Ja, mit interaktiven Releases → release-it
  → Ja, mit manueller Versionskontrolle → changesets
  → Nein → semrel ✅

Brauchst du GitLab-, Gitea- oder Bitbucket-Release-Provider?
  → Ja   → semrel oder Tools mit geeignetem Provider/Plugin
  → Nein → jedes Tool geeignet
```
