## semrel vs semantic-release

**semantic-release** ist der Pionier der commit-getriebenen semantischen Versionierung und wird in tausenden Enterprise-Pipelines weltweit eingesetzt. semrel wurde entwickelt, um dieses Verhalten ohne den Runtime-Overhead zu replizieren.

### Die Node.js-Steuer

Die Integration von semantic-release in eine Go-, Rust- oder C++-Pipeline erfordert:

```bash
# Jeder Pipeline-Job braucht das:
actions/setup-node@v4           # 30–60 Sekunden auf kalten Runnern
npm install -g semantic-release  # 28+ direkte Deps, 400+ transitive
```

In einer minimalen Alpine-Linux- oder Docker-in-Docker-Umgebung bedeutet das **eine vollständige Node.js-Runtime** in einen Container zu ziehen, der sonst nur ein Go-Toolchain enthält.

semrel ersetzt den gesamten Block durch:

```bash
curl -L https://github.com/SemRels/semrel/releases/latest/download/semrel_linux_amd64.tar.gz | tar -xz
./semrel release
```

### Performance in großen Repositories

semantic-release ist bekannt dafür, in Repositories mit vielen Tags und Branches zu zeitüberschreiten. Bei 460 Tags und 65 Branches wurden Ausführungszeiten von über **35 Minuten** gemeldet — wegen sequenzieller Git-History-Traversierung und API-Aufrufe.

semrel ist kompiliertes Go — es traversiert `git log` und fragt Forge-APIs nebenläufig ab. Typische Ausführungszeit bei demselben Repository-Profil: unter **90 Sekunden**.

### Supply-Chain-Angriffsfläche

semantic-release installiert bei jedem Pipeline-Lauf 28 direkte npm-Abhängigkeiten und hunderte transitiver Pakete. Das npm-Ökosystem war wiederholt Ziel von Supply-Chain-Angriffen.

semrel ist eine einzelne, statisch kompilierte Binärdatei. Es gibt keine `node_modules`, keine Laufzeit-Paketauflösung und keine transitive Abhängigkeits-Angriffsfläche.

### Migration von semantic-release

<Card title="Migration in ~15 Minuten" icon="rocket">

1. `semantic-release`-Konfiguration aus `package.json` entfernen
2. [semrel installieren](/de/getting-started/installation/)
3. `semrel release --dry-run` ausführen — die Ausgabe sollte deinen bisherigen Releases entsprechen

</Card>

## semrel vs goreleaser

goreleaser und semrel lösen **unterschiedliche Probleme** und werden häufig zusammen eingesetzt.

| Frage | semrel | goreleaser |
|---|---|---|
| **Welche Version wird released?** | ✅ Berechnet aus Commits | ❌ Tag muss manuell angegeben werden |
| **Für linux/arm64, darwin/amd64 etc. kompilieren** | ❌ Nicht sein Aufgabenbereich | ✅ Kernfunktion |
| **GitHub/GitLab Release mit Assets erstellen** | ✅ Via Provider-Plugins | ✅ Kernfunktion |
| **Changelog generieren** | ✅ Via Generator-Plugins | Teilweise (via Templates) |
| **Auf Docker, Homebrew, npm, PyPI publizieren** | ✅ Via Updater + Packager + Publisher (optional Hooks) | ✅ Kernfunktion |
| **Monorepo-Versionierung** | ✅ Kostenlos | ✅ Nur Pro (948 $/Jahr) |

**Empfohlener kombinierter Workflow:**

```yaml
# GitHub Actions
- name: Nächste Version berechnen
  run: semrel release --dry-run --output json > semrel-output.json

- name: Bauen & verteilen
  uses: goreleaser/goreleaser-action@v6
  with:
    args: release
  env:
    GORELEASER_CURRENT_TAG: ${{ fromJson(steps.prev.outputs.json).nextVersion }}
```

<Aside type="note">
  Wenn du nur automatische Versionierung und ein Standard-GitHub-Release mit Changelog benötigst — ohne plattformübergreifende Binärkompilierung — ist semrel allein ausreichend. goreleaser bietet Mehrwert, wenn du Artefakte für viele Zielplattformen bauen und in Paket-Registries pushen musst.
</Aside>

## semrel vs release-please

**release-please** (von Google) verwendet ein **Pull-Request-first**-Modell. Statt bei jedem Push zu releasen:

1. Sammelt es Commits in einem "Release-PR" an
2. Ein Mensch merged den PR, um den Release auszulösen

Dieses Modell eignet sich für Teams, die vor jedem Release eine menschliche Freigabe möchten. semrel ist vollständig automatisiert — es released bei jedem qualifizierenden Push auf den konfigurierten Branch, ohne PR-Gate. Wähle semrel, wenn du vollständig hands-free CI-Releases willst.

---

## semrel vs changesets

**changesets** ist JavaScript/TypeScript-zentriert und erfordert, dass Entwickler manuell Changeset-Dateien erstellen, die ihre Änderungen beschreiben. Es liest keine Conventional Commits automatisch aus. Wähle semrel, wenn du keinen Developer-Overhead möchtest — schreib einfach Conventional Commits und CI erledigt den Rest.

## Entscheidungshilfe

```
Brauchst du zero Node.js in deiner Pipeline?
  → Ja   → semrel ✅
  → Nein → jedes Tool funktioniert

Brauchst du air-gap / vollständig offline CI?
  → Ja   → semrel ✅
  → Nein → jedes Tool funktioniert

Brauchst du automatische Versionierung aus Commit-Nachrichten?
  → Ja   → semrel oder semantic-release
  → Nein → goreleaser (tag-basiert)

Brauchst du plattformübergreifende Go-Binärkompilierung?
  → Ja   → goreleaser (kann mit semrel kombiniert werden)
  → Nein → semrel ist ausreichend

Möchtest du eine menschliche PR-Freigabe vor dem Release?
  → Ja   → release-please
  → Nein → semrel ✅
```
