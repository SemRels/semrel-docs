semrel unterstützt Repositories mit mehreren unabhängig versionierten Packages.
Es gibt zwei Ansätze — wähle den, der zu deinem Workflow passt.

---

## Option A — pro Package (Matrix)

Jedes Package hat seine eigene `.semrel.yaml` und wird von einem eigenen CI-Job oder Matrix-Step releast.

<FileTree>
- my-monorepo/
  - packages/
    - api/
      - **.semrel.yaml**
      - go.mod
    - ui/
      - **.semrel.yaml**
      - package.json
    - worker/
      - **.semrel.yaml**
      - go.mod
  - .semrel.yaml    Root-Konfiguration (optional, gemeinsame Basis)
</FileTree>

### Tagging-Konvention

semrel präfigiert jeden Tag mit dem Package-Pfad, wenn `tagPrefix` den Pfad enthält:

```
packages/api@v1.4.0
packages/ui@v3.2.0
packages/worker@v0.9.1
```

### Per-Package-Konfiguration

```yaml
# packages/api/.semrel.yaml
schemaVersion: 1
tagPrefix: "packages/api@v"
branches:
  - name: main
plugins:
  - uses: @semrel/provider-github
```

### Releases ausführen (CI-Matrix)

```yaml
jobs:
  release:
    strategy:
      matrix:
        package: [packages/api, packages/ui, packages/worker]
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - name: Release ${{ matrix.package }}
        run: semrel release --config ./${{ matrix.package }}/.semrel.yaml
        env:
          SEMREL_PLUGIN_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

## Option B — Workspace (ein einziger Befehl)

Alle Packages in der Root-`.semrel.yaml` konfigurieren und mit **einem Befehl** releasen.
Packages werden in Abhängigkeitsreihenfolge releast; Packages ohne Neues werden automatisch übersprungen.

### Root-Konfiguration

```yaml
# .semrel.yaml
schemaVersion: 1
branches:
  - name: main
plugins:
  - uses: @semrel/provider-github   # gemeinsames Plugin für alle Packages

workspace:
  strategy: independent    # jedes Package bekommt sein eigenes Semver

  # Option 1: explizite Liste mit optionaler Abhängigkeitsreihenfolge
  packages:
    - path: packages/api
      tagPrefix: "packages/api@v"
    - path: packages/ui
      tagPrefix: "packages/ui@v"
      dependsOn: [packages/api]     # wird erst nach api releast
    - path: packages/worker
      tagPrefix: "packages/worker@v"

  # Option 2: alle Package-Verzeichnisse automatisch entdecken
  # pattern: "packages/*"

  fail_fast: false   # Fehler sammeln (Standard: bei Fehler weitermachen)
```

Jedes Package-Verzeichnis kann eine eigene `.semrel.yaml` haben, die die Root-Konfiguration überschreibt (branches, rules, plugins, tagPrefix).

### Workspace-Unterbefehle

```bash
# Alle konfigurierten Packages auflisten
semrel workspace list

# Vorschau (dry-run, keine Änderungen)
semrel workspace release --dry-run

# Alle Packages in Abhängigkeitsreihenfolge releasen
semrel workspace release

# Unabhängige Packages gleichzeitig releasen
semrel workspace release --parallel

# Bei erstem Fehler sofort stoppen
semrel workspace release --fail-fast
```

### Ausgabe

```

✓ Committed CHANGELOG.md  ✓ Created tag packages/api@v1.3.0
[packages/api]     ✓ released

[packages/worker]  releasing…

```

### CI-Beispiel

## Option A vs. Option B

| Merkmal | Option A (Matrix) | Option B (Workspace) |
|---|---|---|
| Config-Ort | Pro-Package `.semrel.yaml` | Root `.semrel.yaml` |
| CI-Jobs | Ein Job pro Package | Ein Job insgesamt |
| Abhängigkeitsreihenfolge | Manuell (Stage-Abhängigkeiten) | Automatisch (`dependsOn`) |
| Parallelisierung | Native CI-Parallelisierung | `--parallel`-Flag |
| Gemeinsame Plugins | Pro Package duplizieren | Einmalig auf Root-Ebene |
| Package-Isolation | Vollständig | Packages teilen Git-Repo-Kontext |

<Aside type="tip">
  Mit **Option A** beginnen für wenige Packages — einfacher und vollständig isoliert. Zu **Option B** (`semrel workspace`) migrieren, wenn viele Packages vorhanden sind und ein einziger CI-Schritt mit automatischer Abhängigkeitsreihenfolge gewünscht wird.
</Aside>

<Aside type="caution">
  Repository immer mit `fetch-depth: 0` auschecken. Ohne die vollständige Git-Historie kann semrel den vorherigen Release-Tag eines Packages nicht finden.
</Aside>
