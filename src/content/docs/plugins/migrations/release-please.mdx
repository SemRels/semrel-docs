This guide helps teams transition from release-please to semrel without losing release governance.

## Mapping at a glance

| release-please behavior | semrel equivalent |
| --- | --- |
| Release PR with version/changelog updates | semrel analyzer + generator output in CI |
| Tag and release after merge | semrel provider + publish stages |
| PR visibility and review gate | keep branch protection and run semrel post-merge |

## Recommended rollout

<Steps>

1. Keep release-please PR flow temporarily for audit visibility.
2. Run semrel dry-run on merged PRs and compare version/changelog outputs.
3. Move version/changelog ownership to semrel plugins.
4. Move publishing and tag ownership to semrel.
5. Disable release-please release creation to prevent duplicate tags/releases.

</Steps>

## Example plugin baseline

```yaml
plugins:
  - uses: @semrel/provider-github

  - uses: @semrel/analyzer-conventional

  - uses: @semrel/generator-release-notes

  - uses: @semrel/generator-changelog-md
    args:
      file: CHANGELOG.md
```

<Aside type="note">
  If your process requires explicit release review, keep a PR gate in your workflow but ensure that exactly one system creates release tags.
</Aside>

## Risks and checks

- Never allow both release-please and semrel to create tags at the same time.
- Verify monorepo package version behavior before cutover.
- Test rollback by keeping the previous workflow file available for one cycle.
